# RTOS 里的优先级反转：一次调试记录

最近在做一个项目，主控跑 FreeRTOS，任务大致这样划分：

- **控制任务**（优先级 5）：每 10ms 跑一次，算输出。
- **通信任务**（优先级 3）：收上位机指令，偶尔改控制参数。
- **日志任务**（优先级 1）：把状态写进 SPI Flash，频率不高。

现象很诡异：上位机发了一条指令后，控制任务**整段卡死**了几百毫秒，但通信任务和日志任务都还活着。看门狗没复位，说明 CPU 没死，只是高优先级任务被挡住了。

## 定位过程

先怀疑是控制任务里进了临界区没出来，单步跟了一下，临界区进出都正常。然后怀疑中断被屏蔽，`PRIMASK` 也是干净的。

最后在控制任务里加了一个 GPIO 翻转，用逻辑分析仪一看：**控制任务在等一个互斥锁**。

这个锁是通信任务和日志任务共用的 SPI Flash 访问锁。出问题时序是这样的：

1. 日志任务（低优先级 1）拿到锁，开始写 Flash。
2. 通信任务（优先级 3）就绪，抢占日志任务，也想要这把锁，挂起等待。
3. 控制任务（优先级 5）就绪，也要读一次 Flash 状态，同样挂起等待。
4. 日志任务想继续写，但它已经被通信任务抢占了，而通信任务在等锁，控制任务也在等锁……

高优先级被中优先级间接挡住，经典**优先级反转**。

## 修复

FreeRTOS 的互斥锁（`xSemaphoreCreateMutex`）默认带**优先级继承**：低优先级任务持有锁期间，会被临时提升到等待该锁的最高优先级。但前提是你得用对类型。

我之前用的是 `xSemaphoreCreateBinary`，它没有优先级继承。换成 mutex 后：

```c
// 之前
SemaphoreHandle_t flashLock = xSemaphoreCreateBinary();

// 改成
SemaphoreHandle_t flashLock = xSemaphoreCreateMutex();

// 持有期间，日志任务会被临时提到优先级 5，赶紧写完释放
```

改完之后再测，控制任务的卡顿消失，日志任务写 Flash 期间会被短暂提升优先级，写完立刻降回去。

## 一点体会

> 优先级反转不是"死锁"，它不会让你的系统复位，只会让你的高优先级任务"莫名其妙地慢"。

这种 bug 最难抓，因为一切看起来都"在正常工作"。调试时如果发现高优先级任务周期性卡顿，但低优先级任务反而流畅，第一反应应该是查共享资源上的锁。

几个排查信号：

| 现象 | 可能原因 |
| --- | --- |
| 高优任务卡顿，低优任务正常 | 优先级反转 |
| 高优任务完全不动 | 死锁或临界区未退出 |
| 所有任务都卡 | 中断被长时间屏蔽或看门狗即将复位 |
| 偶发卡顿 | 共享资源的临界区过长 |
